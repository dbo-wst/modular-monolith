# 8.2 Domain Model

Aggregates (`Order`, `OrderItem`) are the write model: they enforce invariants, raise domain events (`AggregateRoot`) and are created with `Create` or loaded with `Rehydrate`. Value objects live in `Domain/ValueObjects`. The sample module `Ordering` demonstrates the pattern; replace it with your own domain.

## Domain events

Aggregates record events with `Raise` (every `DomainEvent` carries its own `EventId` and `OccurredOn`) and expose them read-only via `IHasDomainEvents`. Because repositories map aggregates to persistence models, EF Core never tracks the aggregates themselves; instead every repository `Add`/`Update`/`Delete` registers the aggregate with the scoped `DomainEventCollector` (BuildingBlocks.Persistence). After a **successful** `IUnitOfWork.SaveChangesAsync` the unit of work drains the events of all tracked aggregates, clears them, and passes them to `IDomainEventDispatcher` (port in BuildingBlocks.Domain, implementation registered by `AddMediator()`), which invokes every `IDomainEventHandler<TEvent>` of the event's runtime type in-process, in the same DI scope, and stops at the first failed `Fin`. A failed save dispatches nothing and leaves the events on the aggregates. Handlers run after the data is saved but, when called inside `ExecuteInTransactionAsync`, before the transaction commits — a failing handler then rolls the transaction back; outside a transaction the save is already durable, so handlers must not assume they can undo it. To delete an aggregate, call its `Delete()` (which raises the `...Deleted` event) and pass the aggregate to the repository's `DeleteAsync`. Event handlers are discovered by `AddRequestHandlersFromAssembly`. Cross-module or out-of-process delivery (an outbox) is not part of this mechanism.
